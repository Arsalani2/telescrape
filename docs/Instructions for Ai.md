# Instructions for Ai — TeleScrape

> این فایل قوانین دائمی کار برای هر عامل هوش مصنوعی (و توسعه‌دهنده) روی این پروژه است.
> **هر عامل باید قبل از تغییر کد یا مستندات، این فایل را بخواند.**
> زبان مستندات: فارسی؛ کد، دستورها، مسیرها، پیام‌های خطا و شناسه‌های فنی به همان شکل اصلی نوشته می‌شوند.

## 1. Project overview and objectives

- **TeleScrape** یک استخراج‌گر (exporter) برای کانال، گروه و چت شخصی تلگرام است که با کتابخانه [Telethon](https://github.com/LonamiWebs/Telethon) نوشته شده.
- متن پیام‌ها و مدیا (عکس، ویدیو، ویس، موسیقی، فایل و ...) را در یک پوشه‌ی مرتب ذخیره می‌کند و در صورت تمایل فایل زیپ می‌سازد.
- هدف طراحی: اجرا در **Google Colab (حتی روی گوشی)** و همچنین ترمینال معمولی.
- استفاده‌ی مجاز: پشتیبان‌گیری از محتوای خود کاربر یا محتوایی که اجازه‌ی دسترسی به آن را دارد (طبق README).
- مجوز: MIT (فایل `LICENSE`).

## 2. Repository identification and project scope

| مورد | مقدار (تأییدشده از ریپازیتوری) |
|---|---|
| ریپازیتوری | `Arsalani2/telescrape` (https://github.com/Arsalani2/telescrape) |
| شاخه‌ی پیش‌فرض | `main` |
| فایل‌های ردیابی‌شده در زمان تحلیل اولیه | `.gitignore`, `LICENSE`, `README.md`, `requirements.txt`, `telescrape_v3.py` |
| کد برنامه | یک فایل واحد: `telescrape_v3.py` (۱۳۵۵ خط در زمان تحلیل اولیه) |
| وابستگی | `telethon>=1.40` (`requirements.txt`) |

- دامنه‌ی این مستندات فقط همین ریپازیتوری است. ریپازیتوری‌های دیگر کاربر (`VaamYar`, `AvaTTS`, `WhisperSub`, `Mega2Telegram`) بررسی نشده‌اند و ارتباط آن‌ها با این پروژه **اثبات نشده** است؛ بدون شواهد، رابطه‌ای بین آن‌ها فرض نکنید.
- مستندات در پوشه‌ی `docs/` نگهداری می‌شوند (قبل از این کار، ریپازیتوری هیچ پوشه‌ی مستندات یا فایل دستورالعمل AI نداشت).

## 3. Required AI behavior and engineering standards

1. بر پایه‌ی **کد واقعی** کار کنید؛ ریپازیتوری منبع حقیقت است. هیچ مؤلفه، وابستگی یا کار انجام‌شده‌ای را اختراع نکنید.
2. قبل از هر تغییر، کد مربوطه را بخوانید و وضعیت پایه را ثبت کنید.
3. تغییرات را کوچک، قابل بازبینی و قابل آزمون نگه دارید.
4. رفتار فعلی را که در README ادعا شده بدون بررسی کد تکرار نکنید؛ ناهمخوانی‌ها را در `Handoff_Project.md` ثبت کنید.
5. اگر اطلاعاتی نامطمئن یا ناقص است، آن را صریحاً با «Unknown» / «Not verified» / «Not applicable» علامت بزنید.

## 5. Code quality, formatting, naming, testing, and security requirements

### الگوهای موجود کد (مشاهده‌شده در `telescrape_v3.py`)
- پایتون ۳؛ نام‌گذاری `snake_case` برای تابع/متغیر و `UPPER_CASE` برای ثابت‌ها؛ کلاس‌ها `PascalCase` (`Throttle`, `App`, `Stopped`, `DiskLow`, `LoginAbort`).
- تمام متن‌های رابط کاربری از دیکشنری `S` (کلیدهای `fa`/`en`) و تابع `t(key, **kw)` می‌آیند؛ متن جدید باید **در هر دو زبان** افزوده شود.
- بالای فایل فرم Colab با نشانه‌های `#@param` قرار دارد؛ هنگام افزودن پارامتر فرم، همان قالب را حفظ کنید.
- thread‌های کارگر **هرگز `print` نمی‌کنند**؛ فقط از `status()` / `notify()` استفاده می‌کنند و thread اصلی چاپ می‌کند (`_ui_tick`).
- هر فراخوانی شبکه‌ی تلگرام باید timeout و retry داشته باشد (`tg_call` / `download`).
- داده‌ی دریافتی از راه دور هرگز بدون پاک‌سازی در مسیر فایل استفاده نشود (`sanitize`, `safe_ext`).

### تست
- در زمان تحلیل اولیه **هیچ تست خودکار، linter، type-checker یا CI** در ریپازیتوری وجود ندارد (تأییدشده با فهرست فایل‌ها).
- حداقل راستی‌آزمایی فعلی: پارس‌شدن سینتکس (`python3 -I -c "import ast; ast.parse(open('telescrape_v3.py', encoding='utf-8').read())"`). اجرای واقعی نیازمند حساب تلگرام و API credentials است و عامل AI نباید بدون اجازه‌ی صریح کاربر به حساب واقعی وصل شود.
- هرگز ادعا نکنید تستی پاس شده مگر اینکه واقعاً اجرا و پاس شده باشد.

### امنیت
- `API ID`، `API Hash`، شماره تلفن، رمز دو مرحله‌ای، فایل `*.session` و خروجی چت‌ها را هرگز در کد، مستندات، لاگ یا commit قرار ندهید.
- `.gitignore` فعلی این موارد را نادیده می‌گیرد: `telescrape_data/`, `*.session`, `*.session-journal`, `tg_api_credentials.json`, `.env`, `__pycache__/`, `*.pyc`, `.venv/`, `venv/`, `*.part`, `*.tmp`. این فهرست را حذف نکنید.
- قبل از هر commit، diff را برای secret‌ها بررسی کنید.
- وابستگی جدید را بدون ضرورت اضافه یا ارتقا ندهید.

## 6. Instructions for inspecting the code before making changes

1. `README.md` و تمام فایل‌های `docs/` را بخوانید (به‌ویژه `Handoff_Project.md` و آخرین مدخل `Update.md`).
2. `git status` و `git log` را بررسی کنید؛ تغییرات ثبت‌نشده‌ی کاربر را حفظ کنید.
3. بخش‌های مرتبط `telescrape_v3.py` را کامل بخوانید (فایل یک‌تکه است؛ توابع به هم وابسته‌اند — نگاه کنید به `Coding Architecture.md`).
4. ادعاهای `Handoff_Project.md` را با وضعیت واقعی کد تطبیق دهید و سپس ادامه دهید.

## 7. Mandatory synchronization rules for all seven documentation files

- پس از **هر تغییر مهم کد**، هر هفت فایل را ارزیابی کنید و فقط فایل‌هایی را که اطلاعاتشان تغییر کرده به‌روز کنید.
- در پایان هر کار، صریحاً بررسی کنید که هر هفت فایل هنوز دقیق است.
- اگر اطلاعات برای به‌روزرسانی مطمئن کافی نیست، محدودیت را ثبت کنید، نه اینکه حدس بزنید.
- `Update.md` برای هر تغییر مهم مدخل جدید می‌گیرد (قالب در همان فایل).

## 8. Git workflow and change verification requirements

- فقط ریپازیتوری و شاخه‌ای که کاربر مجاز کرده استفاده شود.
- قبل از تغییر: ریپازیتوری/شاخه را تأیید کنید، working tree را ببینید، کوچک‌ترین مجموعه‌ی تغییر ایمن را مشخص کنید.
- بعد از تغییر: مستندات را به‌روز کنید، راستی‌آزمایی‌های موجود را اجرا کنید، **کل diff** را بازبینی کنید، secret‌ها را جست‌وجو کنید.
- commit/push فقط وقتی مجاز و مناسب است؛ مقصد ریموت و شاخه را قبل از push تأیید کنید.
- انتهای پیام commit (طبق تنظیمات این نشست): 
  `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` و خط `Claude-Session: ...` مربوط به همان نشست.
- هرگز: force-push، بازنویسی تاریخچه‌ی Git، حذف فایل یا دور ریختن تغییرات کاربر بدون اجازه‌ی صریح.
- هرگز نگویید فایلی در GitHub است مگر اینکه push واقعاً موفق شده باشد.

## 9. Rules for preserving historical records

- مدخل‌های `Update.md` را هرگز حذف، بازنویسی یا جابه‌جا نکنید؛ فقط به انتها اضافه کنید.
- اگر مدخلی خطا دارد، آن را نگه دارید و در انتهای فایل یک **اصلاحیه‌ی تاریخ‌دار** با ارجاع به مدخل اصلی اضافه کنید.
- به‌جای بازنویسی کامل یک فایل مستندات، ویرایش موضعی و افزایشی انجام دهید.
- اطلاعات منسوخ را «Superseded» علامت بزنید و جایگزین را توضیح دهید؛ بی‌صدا حذف نکنید.
- پس از ویرایش، بررسی کنید که محتوای نامرتبط و تاریخچه دست‌نخورده مانده است.

## 10. Rules for handling uncertainty and incomplete information

- هر مقدار تأییدنشده را با `Unknown` / `Not verified` / `Not applicable` علامت بزنید.
- بین «تأییدشده با کد»، «استنباط‌شده» و «پیشنهادی» تمایز صریح بگذارید.
- نام مدل، زمان، نتیجه‌ی تست، hash کامیت یا موفقیت push را هرگز اختراع نکنید.
- اگر دسترسی (ریپازیتوری/مجوز/credential) نبود، محدودیت را توضیح دهید و کمترین اطلاعات لازم را بخواهید.

## 11. Updating the handoff document before ending a substantial task

قبل از پایان هر کار قابل‌توجه: `Handoff_Project.md` را به‌روز کنید (وضعیت فعلی، آخرین عملیات موفق، موانع، گام‌های بعدی با اولویت) و مدخل `Update.md` را اضافه کنید. همچنین طبق ترجیح کاربر، فایل ریشه‌ی `PROJECT_HANDOFF.txt` (فارسی، متن ساده UTF-8) را به‌روز نگه دارید؛ این فایل خلاصه‌ی کوتاهی است و به `docs/Handoff_Project.md` ارجاع می‌دهد.
